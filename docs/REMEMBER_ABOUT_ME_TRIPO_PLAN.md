## 1. 这次要解决的问题

目标是制作有校园建筑围合感、服务 Persona 争夺的大学社团中庭。不能把六个彩色摊位围成一圈就视为完成地图。需要同时控制校园空间、游戏可达性、几何风格和可拆分资产。

第一轮用户已经选择：

1. **A：可导入团结/Unity 的模块化地图，并接入现有玩法。**
2. **C：两层都能行走，并保留可上下的楼梯。**
3. **A：中央留空，小型几何树移到外围作为固定装饰。**
4. **A：Tripo 生成有造型要求的独立资产；地面、布局、掩体和碰撞精确搭建。**

确定采用的路线：保留校园建筑语言；先做精确的双层可玩布局；Tripo 生成建筑样板与独立大手等造型资产；统一材质后组装。地面、二层走廊、楼梯、开口与功能边界由可编辑结构保证。单层方案、仅背景二层和整图一次生成不再是执行路线。

用户最新补充已确认：

- 两层通过楼梯连接；二层各段走廊直接互通，不做互相隔离的独立阳台。制作基线采用沿建筑连接的开放 U 形回廊，左右楼梯通往一层；U 形是满足连通要求的设计落点，具体拐角和长度可以在草模中调整。
- 从二层落到一层也算坠落：落地后角色不传送，韧性值直接清零，并固定掉落 1 个 Persona。
- 六社团按视觉参考采用一层两个、二层四个；以一层创客/桌游、二层音乐/摄影/动漫/篮球为初始安排，具体位置可为动线与画面调整，无需就每个位置重复询问。
- 二层社团小房间暂不制作可玩内部；从外面能看出房间和纵深即可。按暂不进入房间规划，保留走廊、门窗与立面。
- The Hand 可以击打二层。优先表现为一层掌拍、二层握拳拳击；核心要求是手的动作和角色发生合理的击打或接触。
- 中央主战区、几何低模、纯色轻明暗、纸箱和垃圾桶是仅有的动态公共物理道具等原有要求继续有效。

上述三项均已得到明确回答，不再列为待选。上下楼梯按正常移动处理；角色跳下、失足或被击出二层边缘进入下层，按一次坠落结算，不通过不稳定的落地速度阈值猜测。

### 坠落结算与韧性

二层到一层的落地事件由服务器一次性完成：确认跨层坠落→韧性设为 0→掉落 1 个可掉落 Persona→保留一层落地位置。韧性清零不得再经通用破防逻辑为同一落地追加第二次掉落，也不能同帧被旧的韧性重置分支立即恢复为正数。

一次腾空过程使用独立事件标识，持续碰撞回调只结算一次。正常落地后结束该事件，之后再次离开地面形成新的坠落；不能把多次真正的坠落误合并为一次。从二层直接掉到地图外而没有在一层落地，按一次出界坠落处理，不先虚构一次二层落地来扣第二个 Persona。

清零后的恢复速度、是否有短硬直沿用现有机制作为起点，后续调试时检查，不把新的硬直时长写成用户已确认规则。身上没有可掉落 Persona 的边界情况仍需单独确定，不能凭空创建 Persona。

### 房间与立面的制作约定

二层使用“可从外部辨认的浅层室内布景”：门窗框、短侧壁、顶面和后墙形成深度，后墙使用社团色块与大型几何图标。它是封闭的视觉模块，不建立深房间、内部路线或可滚入 Persona 的夹层。

建议通过关闭的门、窗框或清晰的固定挡栏表达不可进入，避免看起来敞开的门口被无形碰撞挡住。室内不摆放大量小物件。楼梯、平台与走廊仍是真实可通行结构，不因房间简化而省略。

## 4. 为什么不能直接把这两张图当作多视角输入

Tripo 的 multiview-to-model 面向同一物体的 front/left/back/right 视图，要求视图一致，至少包含正面和另一个方向。效果图与带文字的功能平面图不是这样的视图组合。

正确分工：

- 设计融合：两张参考图可以作为 image-to-image 的不同参考，明确“图一取建筑、配色和一层两社团/二层四社团；图二取中央争夺与外围浅空间关系”。加入最新确认的连通二层和中央留空要求；不复制图二四社团后排的旧排布。融合图仍需人工核对，不能假定模型遵守全部约束。
- 单件生成：给 image-to-model 一张清晰、完整、少遮挡的模块参考图。
- 多视角生成：只有在资产背面或侧面有重要结构时，才提供同一模块的一致正面/侧面/背面图。优先从同一可控设计输出视图；AI 补出的多视图也要逐张核对。
- 图二中的标题、说明框、红点和其他设计标记不得作为纹理印到场景中。

image-to-model 不依靠额外长篇规则提示词来修正布局；参考图本身必须表达所需结构。坠落、返回、Recover、Eat 与打断规则保存在设计和代码中，不要求 3D 生成接口实现它们。

### The Hand 的两层动作设计

一层：从天空进入，手掌朝向广场，预警后向下拍击，接触后抬起撤回。二层：先到达目标回廊上方或面向广场的开放一侧，握拳并挥击；朝向依据目标位置与建筑避让确定，不让拳头穿越屋顶和墙体才打到人。二层活动边缘需留出手的进入空间，屋檐不能完全遮住走廊。

建议动作阶段统一为“出现与预警→蓄势→有效击打→撤回”。服务器使用与可见手掌/拳头匹配的简化击打范围，仅在有效击打阶段检测；快速挥拳需防止跨帧漏碰，同一次动作对同一角色只登记一次击中。手经过或撤回时的视觉接近不自动连续触发伤害。

资产优先采用同一手部造型，本地制作简单手指关节和开掌/握拳两姿态，保持大小、颜色、腕部和几何语言一致。独立手部不等同于完整人形，不假定 Tripo 的通用角色自动绑定可以直接完成它，也不默认购买绑定和动作重定向。

如果首个手部模型不适合本地改变姿态，备选为同参考体系下分别生成开掌和拳头模型，在手位于场外/预备阶段切换，两种击打都使用整体运动。此备选会增加一次参考图和一次 3D 生成，须列入后续执行单。用户强调合理接触，现阶段不要求复杂逐指表演。

### 7.1 每个资产一张制作卡

记录：资产编号、用途、目标包围盒、朝向与支点、固定/动态、可见方向、面数上限、颜色方案、禁用细节、参考图、验收标准。

例：`CAMPUS_BAY_01`，二层社团房间立面；门窗框、短侧壁与后墙产生浅层室内纵深，入口不可进入且有可见边界；模块不包含可行走楼板和楼梯，这些另行精确搭建；独立纯色背景；同一视图中不出现其他楼栋、文字说明、角色或天空大手。

先准备清晰三分之四视角，保证正面和一侧可见；复杂背面需要第二张一致视图。光照柔和，不用强阴影假装几何凹槽，不用写实砖纹、脏污、木纹和复杂 PBR。

### 7.2 候选参数

- 默认几何模型：`tripo-p1` → `P1-20260311`，适合本次简化低模试样。
- 首个立面试样：`face_limit=6000`；The Hand 初始建议 `face_limit=4000`。这是逐件试样预算，实际以轮廓和清理结果调整，不再给整张地图套一个随意的面数上限。
- 推荐几何优先：`texture=false, pbr=false`，生成后使用共享纯色材质或顶点色。单件生成结果可能只有一个材质，需要本地按部件/面分配颜色，不能承诺自动得到可编辑色块。
- 若选择保留生成颜色：`texture=true, pbr=false, texture_quality=standard`。这仍会生成颜色贴图，并不等于“没有贴图”；需去掉写实细节和过重的烘焙阴影。
- 不默认启用 P2、quad、HD、8K、smart_low_poly 或自动分件。P1 不支持 generate_parts，不能靠此参数把整图自动拆成正确游戏模块。
- 先验收 GLB；项目需要 FBX 时再转换。`game-mobile` 预设会附加付费转换，正式调用前需展开完整链条。
- `auto_size` 不能替代地图尺寸校准。导入后以角色和布局网格检查单位、旋转和支点；后续有转换时在最后步骤统一坐标。

### 7.3 正式调用的操作顺序

1. 免费检查账号、网络、余额；使用前一轮已经验证有效的系统代理路径，不在日志中输出密钥。
2. 将输入图片保存为稳定的项目文件，避免微信临时目录清理后丢失。
3. 运行确切命令的 `--dry-run --json`，核对模型实际版本、端点、上传图片和全部处理步骤。
4. 按已确认方案提交单个小样，等待完整结束并保存任务记录。
5. 同时看实际 GLB 和渲染图；不能仅用流程返回的概念图验收。
6. 通过后推进下一项；不合格先区分参考图错误、重建错误和可本地修复的问题，不自动反复抽卡。
7. 记录每项实际扣费及累计费用。失败任务退回冻结额度；成功但视觉不合格的任务通常仍计费，不将两者混淆。

## 9. 地图与玩法接入不能漏掉的部分

现有项目采用服务器权威的简化空间判定，仅导入模型、添加客户端 Collider 并不足够。

本轮只读检查发现：

- `GameModel.cs` 的 `Floor()` 当前用 x/z ±14 判定旧地面，障碍由固定坐标数组描述。
- Persona 掉落安全位置目前夹到 x/z ±11；越界回收阈值和返回位置也使用旧地图范围。
- 默认动态公共道具仍有 chair、box、trash，需要按明确需求去掉 chair。
- `fallDrop=1` 已存在；但高处落地还有另一条掉落分支。二层落地现在要求韧性清零、掉 1 个 Persona、不传送，需要统一事件处理；防止同次落地被高处落地逻辑和韧性破防逻辑重复结算，不要只调原有落地速度阈值。
- 周期 The Hand 当前按目标玩家位置拍击；新需求要求按目标所在楼层选择掌拍或拳击，并验证服务器击中范围与可见动作吻合。

正式接入建议将地面边界、掩体、返回点、Persona 安全落点和拍击区域放进同一地图定义，由服务器与显示层共同使用。先用基础几何验证移动和坠落，再替换美术外观。

**双层地图新增工作：**现有 `Floor(x,z)` 风格的单层高度查询不能直接用二层高度替换，否则一层玩家可能被顶到二层或被上层地板挡住。需要结合角色当前高度、移动路径和支撑层处理上下层地面；楼梯显示可用台阶，实际行走采用匹配的简化坡道；检查阶梯入口、下楼、跳下、桥下通行、抓人跨层距离和 Persona 在楼层间的落地。服务端与客户端必须使用一致的双层空间定义。

双层布局的初始尺寸只作草模起点：层高 4.5 m、上层走廊净宽 4.5 m、楼梯净宽 4 m；最终以角色体积、抓取距离、相机遮挡和争夺路线测试调整。若楼梯坡度按约 30°设计，4.5 m 层高需要约 7.8 m 水平展开，平台另计，应在布局阶段预留，不能到贴美术时才补楼梯。

用户已选择 80×64 m 总占地与约 36×30 m 中央区。现有移动速度为 5.5 m/s，等长直线横穿 80 m 约需 14.5 秒，横穿中央 36 m 约需 6.5 秒；两者都不代表建筑间必定存在直通路线。结合 2–6 人测试入口到中心、楼梯到中心与二层两翼之间的真实移动时间。现有 Eat 2.5 秒、Recover 1.5 秒，应检查扩大后仍有接近、打断和争夺机会，不默认修改这些时长或角色速度。

## 10. 验收标准

| 类别 | 必须检查 |
|---|---|
| 校园辨识 | 有建筑立面、柱廊和空间围合；不是缩小的桌面摊位陈列 |
| 参考一致 | 建筑风格及一层两社团/二层四社团来自图一；中央争夺与外围浅空间来自图二；最新确认规则优先 |
| 可玩范围 | 中央连通；二层各段走廊互通并由楼梯连接一层；外围空间浅，房间仅有视觉纵深，无深室 |
| 社团识别 | 从实际游戏相机、移动端尺寸看，六社团能依颜色和大图标区分，无文字依赖 |
| 中央争夺 | The Hand、Persona 掉落与 Recover/Eat 可见；遮挡与掩体允许接近和打断 |
| 坠落 | 指定开口确实可坠落；每次有效坠落只触发一次规则；返回点可达且不立即再次坠落 |
| 二层落地 | 从二层跳下、失足或被推出后在一层落地：韧性恰为 0，掉落恰为 1 个 Persona，角色位置保留在落点；正常走楼梯不误触发；同一坠落不重复结算 |
| Persona | 不滚进墙后、桶内、地图下方不可达区域或装饰死角；落到可达的一层不视为异常；异常位置有受控恢复；不凭空复制或误删 |
| 道具 | 动态公共道具仅纸箱、垃圾桶；独立碰撞、状态与网络编号；建筑装饰固定 |
| The Hand | 独立于场景；一层掌拍、二层拳击能合理接触角色；避开穿墙；一次动作一次有效命中；开局 Reveal 与周期事件分开验证 |
| 材质 | 纯色、轻微面明暗，无写实纹理、复杂材质或无法解释的强烘焙阴影 |
| UI 一致性 | 与当前首页和战斗 HUD 并排检查；奶油中性色大面、粉彩识别、深蓝灰结构框协调；不把 UI 按钮、文字或旧场景材质带入新地图 |
| 空间尺度 | 总占地 80×64 m，中央约 36×30 m；实际可玩面积按草模统计；走廊和楼梯连通，角色与道具尺度不随占地同比放大 |
| 技术 | 单位、支点、朝向、面数、材质数、碰撞和服务端地图定义一致 |
| 性能 | 在约定移动设备或 WebGL 环境测实际帧率、内存和绘制开销；不能仅凭低面数宣称达标 |
